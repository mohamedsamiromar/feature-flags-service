## Key Architectural Decisions

### Cache Key Scope
`flags:{project_id}:{env_id}:{flag_key}` — written in exactly one place,
`FlagEvaluationService._cache_key`. Including `env_id` means production and staging
caches are independent: a staging deploy never degrades production hit rates. Never
format the key by hand; a second copy of that string is how a pre-tenancy version of
this code evicted one key while evaluation read another.

### Eviction and `config_version` Move Together
`FlagService._invalidate_env_caches` does both, and every eviction path funnels through
it. `config_version` is the ETag for the config download, so evicting without bumping
leaves an SDK polling a version that never moves while the server serves something new.
`_evict_env_caches` is the eviction-only half, so a segment fan-out bumps once for the
whole set rather than once per flag. Bumps are an atomic `F()` update.

### Membership Isolation
Every queryset is scoped by project membership (`organization__memberships__user`), not
by an owner FK. This is the multi-tenancy boundary. Not a member → 404; member with too
low a role → 403.

### SDK Key Storage
Only the SHA-256 hash is persisted; the 16-char prefix is stored for display and the
full key is returned exactly once. `AuditService.REDACTED_FIELDS` strips `hashed_key`
from snapshots, because hash-only storage is only meaningful while the digest lives in
one table.

### Uncertainty Fails Closed
An unresolvable prerequisite, an unknown segment key, or a `gt`/`lt` operand that will
not coerce all match nobody. **Never invert an unresolvable reference** — a
`not_in_segment` rule that matched on failure would turn one dangling reference into a
full rollout, and `lt` written as `not gt` would match every user whose attribute is
unusable.

### Soft-Delete vs Hard-Delete
Archive preserves audit history, evaluation logs, and rule config. Unarchive is a
zero-loss one-call restore.

### Async Evaluation Logging
`EvaluationLog` writes go through Celery, keeping the SDK hot path free of DB write
latency. `log_evaluations` takes a whole batch and carries `context_data` **per record**
— an impression flush spans many users, so a shared context would force one request each.

### Three-Layer Validation
`rollout_percentage` (0–100) is enforced at the DRF serializer, the Django model
validator, and a PostgreSQL `CheckConstraint`. Any new numeric invariant should follow it.

### Conformance Vectors Are Generated, Never Written
`GET /sdk/flags/config/` ships the raw ruleset, so every SDK reimplements the engine.
`apps/evaluation/conformance.py` builds a fixture with **explicit pks** (rule-level
bucketing is salted with the rule id, so sequence-assigned ids would differ per machine)
and runs `FlagEvaluationService` over it. Any change to evaluation behaviour changes the
file; regenerate and review the diff, because it is the record that an SDK contract moved.

## Known Constraints and Gotchas

- **Celery does not auto-reload.** After editing `tasks.py`, `docker compose restart
  celery`. Change a task signature without it and the web container queues the new shape
  while the old worker rejects it — the endpoint still returns `202` and nothing is
  written. In a real deploy, workers go first.
- `SDKKeyFactory._create` attaches `instance._full_key` for tests that authenticate with
  the key. Test-only; real `SDKKey` instances have no such attribute.
- Tests that assert on rows written by a task need the `eager_celery` fixture. Otherwise
  `.delay()` hands the batch to the real broker and the worker writes it to the
  *development* database, so the assertion silently checks nothing.
- `celerybeat-schedule` is a binary produced by the beat scheduler and is gitignored.
- `CONN_MAX_AGE=60` keeps PostgreSQL connections alive across requests.
- `EvaluationLog` has **no rollup**. It answers "what was served", not "how often over
  time". This is why the bootstrap endpoint logs nothing.

## Infrastructure Topology

| Service | Port | Redis DB |
|---|---|---|
| Django web | 8000 | — |
| PostgreSQL | 5434 → 5432 | — |
| Redis | 6379 | DB 0 = Celery broker, DB 1 = flag cache |
| Celery worker | — | — |
| Celery beat | — | — |

`db` and `redis` both declare named volumes, so `docker compose down` keeps the data.
`down -v` is the deliberate clean slate.

## Test Infrastructure

- Factories in `conftest.py` (project root): `UserFactory`, `OrganizationFactory`,
  `MembershipFactory`, `ProjectFactory`, `FeatureFlagFactory`, `EnvironmentFactory`,
  `EnvironmentFlagFactory`, `VariationFactory`, `SDKKeyFactory`
- `personal_project_for(user)` gives a deterministic per-user org + project, so a flag
  and an environment created with the same `owner=` shim land in the same project
- `auth_client` provides a pre-authenticated `APIClient`; `sdk_key` an active server key
- Tests hit real PostgreSQL and Redis — no ORM mocking
- An autouse fixture clears the cache around every test: Redis outlives the test
  database, so a recycled pk could otherwise read a previous session's entry
- CI additionally runs `makemigrations --check` and
  `generate_conformance_vectors --check`
